# Future migration: move guest photos to Cloudflare R2

## Why we'd do this
Supabase's free tier gives us 1 GB of storage and 50 MB/day of bandwidth.
The Memories feature stores ~5 MB per upload (original + thumb). When the
Supabase dashboard shows the project at ~70% of free-tier usage,
migrating photo files to R2 is way cheaper than upgrading to Supabase
Pro ($25/mo).

**Cost comparison at 100 GB of photos:**
- Supabase Pro: $25/mo flat
- Cloudflare R2: ~$1.50/mo storage, $0 egress

R2 has no egress fees — that matters because every time a guest opens
the gallery or lightbox, photos get served from somewhere, and Supabase
counts that against egress.

## What stays the same
- The Supabase Postgres database keeps the `memories` table. Tiny rows.
  Effectively free forever.
- Page UI, RLS policies on the metadata table, the upload form, the
  gallery, the lightbox — none of that changes.

## What changes
- Photo binaries move from the Supabase `memories` storage bucket to a
  Cloudflare R2 bucket.
- `publicPhotoUrl()` and `thumbPhotoUrl()` get rewritten to point at the
  R2 public bucket URL.
- The upload code uses an S3-compatible client (`@aws-sdk/client-s3`) or
  the R2 REST API instead of `supabase.storage.from(...)`.

## Step-by-step

### 1. Set up R2 (~15 min)
1. Cloudflare account → R2 → Create bucket: `falls-memories`.
2. Settings → Public access → enable "Allow Access". Note the public
   bucket URL (looks like `https://pub-<hash>.r2.dev`).
3. API Tokens → Create API Token → "Object Read & Write" on the
   `falls-memories` bucket only. Save the Access Key ID + Secret.
4. (Optional) Hook a custom subdomain like
   `memories.thefallsatlionsden.com` to the bucket via Cloudflare DNS.

### 2. Migrate existing photos (~30 min one-time)
Write a one-shot script (`scripts/migrate-supabase-to-r2.mjs`) that:
- Lists every row in `public.memories`.
- For each row, downloads `<id>.jpg` and `<id>-thumb.jpg` from Supabase
  storage.
- Uploads both to R2 under the same paths.
- Updates the row's `storage_path` if needed (probably stays the same).
After the script finishes, verify the gallery renders against R2 by
temporarily swapping `publicPhotoUrl()`.

### 3. Swap the runtime code (~30 min)
- Add Vercel env vars:
  - `R2_ACCESS_KEY_ID`
  - `R2_SECRET_ACCESS_KEY`
  - `R2_BUCKET_PUBLIC_URL` (the pub-<hash>.r2.dev or custom domain)
- Replace `src/lib/supabase.ts` storage helpers with R2 versions.
  Uploads from the browser will need *signed URLs* generated by a
  small Next.js API route (`/api/memories/sign-upload`) because R2
  doesn't support anonymous public writes the way Supabase storage
  does. The API route runs server-side, holds the R2 secret, and
  returns a one-time presigned PUT URL for the client to upload to.
- Update `publicPhotoUrl()` / `thumbPhotoUrl()` to point at the
  R2 public URL.

### 4. Tear down the Supabase bucket
Once everything is verified live, delete the Supabase `memories`
storage bucket via the dashboard. Saves both storage and egress
counters for the database tier.

## Estimated effort
- One afternoon end-to-end. The hardest part is the signed-URL API
  route + the one-time migration script.

## Notes
- Keep the existing `memories` Postgres table. R2 has no database. We
  still need a place for captions, names, place tags, timestamps, and
  the Supabase free tier handles that essentially for free.
- If we ever want full auth (user accounts, "my photos only") that's
  also still Supabase territory. R2 is purely the binary store.

## Why not do this now?
At our current usage, R2's $1.50/mo and Supabase's $0/mo come out the
same. The cost flip happens around the 1 GB mark, which is hundreds of
guest uploads. No reason to migrate until we approach that.
